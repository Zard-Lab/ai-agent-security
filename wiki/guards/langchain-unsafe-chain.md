# LangChain chain executes model output without sandboxing

**Guard ID:** `langchain-unsafe-chain`
**Module:** `agentsec/guards/langchain_unsafe_chain.py`
**Severity:** HIGH (both checks)
**Standards:** OWASP-LLM:LLM02, OWASP-LLM:LLM05

## Threat

When an LLM's response is directly executed as code or shell commands, any successful
prompt injection attack becomes arbitrary code execution. LangChain's `langchain_experimental`
package ships chain types that do exactly this — placed there precisely because they are dangerous.
These chains offer no sandboxing, no output-schema validation, and no execution timeout.

## Complementarity with other guards

| Guard | What it detects |
|---|---|
| `agent-tool-overpermission` | New tool API: pydantic-ai `@agent.tool`, LangChain `ShellTool`/`PythonREPLTool` |
| `langchain-unsafe-chain` | Legacy LangChain chain API: `LLMBashChain`, `PALChain`, `LLMMathChain` |
| `llm-output-to-sink` | Direct wrapping: `exec(agent.run_sync(...))` |
| `command-injection` | Subprocess with dynamic args via HTTP (regardless of agent context) |

The four guards address independent surfaces within the same threat model (model output executed).

## Detection design

Two independent checks, each emitting at most one finding:

### 1. `dangerous-chain-imported` (HIGH)

**Signal:** Import of a LangChain chain class that executes model output as code or shell.

**Dangerous classes:**
- `LLMBashChain` — passes model output to the local shell via subprocess
- `PALChain` (Program-Aided Language model) — executes Python generated by the model
- `LLMMathChain` — evaluates mathematical expressions via Python `eval`

```python
# Fires:
from langchain_experimental.llm_bash import LLMBashChain
from langchain_experimental.pal_chain import PALChain
from langchain.chains import LLMMathChain  # legacy path

# Silent (safe retrieval chain):
from langchain.chains import RetrievalQA
from langchain.chains import ConversationalRetrievalChain
```

**Silence conditions:**
- Any file contains `# security: allow-langchain-unsafe-chain`

### 2. `allow-dangerous-code` (HIGH)

**Signal:** `allow_dangerous_code=True` is set anywhere in the codebase.

Newer LangChain versions require this explicit opt-in for dangerous chains — detecting the flag is
equivalent to confirming the dangerous execution path is active.

```python
# Fires:
chain = PALChain.from_math_prompt(llm, allow_dangerous_code=True)
chain = LLMBashChain.from_llm(llm, allow_dangerous_code=True)

# Silent:
chain = PALChain.from_math_prompt(llm)  # flag absent → guard not triggered
```

**Silence conditions:**
- Any file contains `# security: allow-langchain-unsafe-chain`

## Severity rationale

Both patterns enable prompt-injection-to-RCE:
`LLM prompt injection → model generates malicious code → chain executes it → RCE`

HIGH is appropriate because:
- The attack path requires zero additional steps once injection succeeds
- The execution runs with the same privileges as the process user
- No sandboxing or timeout is provided by default

## Known bypasses / false negatives

| Pattern | Caught? | Notes |
|---|---|---|
| `LLMBashChain` imported and used | Yes | Primary case |
| `PALChain.from_colored_object_prompt(llm)` | Yes | Same import |
| `LLMMathChain.from_llm(llm)` | Yes | Evaluates Python for math |
| Chain built dynamically via reflection | No (FN) | Hard to detect without execution |
| `subprocess.run(llm.predict(cmd))` without chain | No (FN) | Caught by `llm-output-to-sink` or `command-injection` |
| `allow_dangerous_code=False` (explicit safe default) | No (safe) | Flag value is False; guard only fires on True |
